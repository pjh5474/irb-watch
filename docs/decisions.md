# IRB Watch: design interview record

Recorded 2026-11-04. Each entry is a question asked before planning, the answer given, and the reason. The approved plan is in `docs/plan.md`.

## Scope
- This repo is the **server only**. The frontend (Next.js) lives in a separate repo.
- Supabase (Postgres + Auth) is the database. The schema and migrations live **in this repo** under `supabase/migrations/`.
- The frontend reads data **directly from Supabase** (supabase-js + RLS). This server mostly writes, using the service-role key, and exposes few endpoints.

## Decisions

| Topic | Decision | Reason / note |
|---|---|---|
| Language | Python 3.11+, managed with uv | Better parsing libraries (PDF, HWP, OCR) than JS |
| Framework | FastAPI | Async, typed, auto OpenAPI docs |
| Agent role | Fixed pipeline. The OpenAI agent only summarizes diffs and ranks priority | Change detection must be deterministic and reproducible |
| Model control | `OPENAI_BASE_URL` + `OPENAI_MODEL` env vars, pointing at an OpenAI-compatible API gateway | User wants to switch models at the gateway. **Gateway not chosen yet** |
| URL source | Admin-managed global list. Users subscribe to items from it | Each URL is scanned once however many users follow it |
| Accounts | Created by admin only. Users log in with Supabase Auth afterwards | |
| Server auth | Verify Supabase JWT. Admin role gates admin endpoints (manage URLs, create users, trigger scans) | |
| Trigger | Built-in scheduler (APScheduler) plus an API endpoint | |
| Deploy | Single long-running container. A DB lock keeps later scaling safe | |
| Trackable unit | Linked files (PDF/HWP/DOCX) plus the page's own text | Catches notices as well as attachments |
| Storage | **Revised 2026-11-04:** store originals in a **private Supabase Storage bucket**, named by sha256. DB keeps the storage path (not a URL), hash, extracted text and the source post URL. Frontend gets short-lived signed URLs | Hospitals delete old versions; the site's download links are encrypted tokens, not permanent. Cloudflare R2 considered and deferred (negligible gain at this volume). Check hospital terms before sharing copies beyond internal users |
| Fetching | httpx by default. Playwright fallback per URL, set by a `needs_browser` flag | Keeps the image light unless JS rendering is needed |
| Login-only boards | **Added 2026-11-06.** A source with `config.login_user` logs in at the start of every scan with that user's stored ID/password (headless Playwright fills the site's own form, one attempt, cookies kept in memory only, then discarded). Credentials: Windows Credential Manager via `keyring`, key `<user>/snuh-<board_key>`, entered by the owner with `scripts/save_credentials.py`; never in the repo or read by the assistant. `scripts/save_login.py` (manual login, cookies in `data/sessions/`) is for exploring only | The site ends a session after 30 minutes idle, so a saved session cannot serve a daily scan. A wrong password is never retried (account lockout). Several sessions per account can coexist (tested live) |
| Login failures | `LoginRejectedError` (login refused, no stored credentials) and `LoginExpiredError` (login page where content was expected) set only that source to `needs_review` with the reason. A dead session mid-scan fails the scan; it is never recorded as one broken post per post | One site's login trouble must not stop other sources, and must not look like "no change" |
| Access to login-only content (SUPERSEDED 2026-11-09 by "Study sources"; kept as history) | **Applied 2026-11-06; read policies verified with six impersonated test users in a rolled-back transaction (follower without proof, valid proof, expired proof, proof without following, admin, public-only follower). Not yet tested: the endpoint with a real non-owner hospital account.** A source with `requires_login` is readable only by admins and by users who hold an unexpired proof in `source_access` (the "follow it" condition was dropped 2026-11-09, see "No subscriptions"). The proof is created by `POST /sources/{id}/access`: the user's OWN hospital ID/password are used once in memory (headless login, then one request for that board), never stored or logged; success = 30 days (`ACCESS_TTL_DAYS`), then the user logs in again. One rule, `private.can_read_source()`, backs the read policies of documents, versions, files and news cards, and the server's summary check mirrors it. Users stored copy is searched/read after proof; there is no live per-user search. `requires_login` is set when an admin gives a source a `login_user` and is never cleared automatically. Abuse guards, both counted from the audit log: 5 login checks per app user per hour (`ACCESS_ATTEMPTS_PER_HOUR`), and **3 failed logins per hospital ID per hour across all users** (`ACCESS_ID_FAILURES_PER_HOUR`), so several users cannot lock one hospital account together. The ID is logged only as `HMAC-SHA256(ACCESS_ID_HASH_KEY, trimmed lower-cased ID)` in the payload (`id_fp`) of `access.attempted/granted/denied`; the audit table never holds hospital IDs. A hospital ID's count = attempts minus granted minus denied-without-judging (`board_not_readable`, `check_failed`); an attempt with no logged result counts as a failure (safe direction). With no `ACCESS_ID_HASH_KEY` set, access checks answer 503 and try no login | Today any user can insert a subscription and read login-only data. A stored password is not proof of access; a successful login against that board is. Hospital access can be revoked, hence the expiry. Risk: our server briefly handles a user's hospital password; users must be told, and the endpoint must stay HTTPS-only |
| No subscriptions | **Decided 2026-11-09; migration `drop_subscription_requirement` written, NOT yet applied (waiting for the owner's go); offline tests only.** Admin and the scheduler scan; users only read. Every signed-in user may read every source (`private.can_read_source` = admin, or the source exists and is public, or the user holds an unexpired `source_access` proof). Scans keep using the admin's stored login; a user's own hospital login is still only a 30-day proof, used once in memory and never stored. `sources.is_active` is still ignored by the read rule (history of deactivated sources stays readable). `public.subscriptions` is kept with its audit trigger; `insert` is revoked from `authenticated`, so users cannot add rows; dropping the table is a later decision. Search over stored text stays out of scope | The only user-side choice was following a source, and every read rule required it; the owner wants a read-only user role. Consequence: news cards (`audit_logs`, category `document`) show to all users for readable sources, so the frontend can no longer filter a feed by subscription. The per-user caps on summaries (20/day) and download links (200/day) still bound cost and bulk copying |
| Study sources | **Decided 2026-11-09. Code and tests are done (offline only); migration `study_members_and_ai_switch` is written and dry-run, NOT applied (waiting for the owner's go).** A study is a members-only source (`requires_login`) scanned with its own stored hospital account (`login_user` label + the credential table; an admin types it on an admin page, write-only). **Readers:** admins, and users an admin assigned in `source_members(source_id, user_id)`; one rule, `private.can_read_source()`, for documents, versions, files, news cards and now the `sources` rows themselves (a non-member does not see that a study exists). | Newest 50 posts per board | **Decided 2026-11-10 (owner). Built and tested offline.** `MAX_DOCS_PER_URL` = 50 for every source (was 200, and more than that failed the whole scan). Each scan still reads the **whole list** (cheap), but opens only the newest 50 posts (posted date, then post number, so a pinned old notice does not take a place) and downloads only their files. The rest are reported as unreadable to change detection, like secret posts: **neither seen nor missing, never removed** for being outside the window; a post that disappears from the list itself is still removed after 2 scans. Posts stored earlier that fall outside the window **stay stored, frozen at their last version** (owner: keep, not delete). The scan's `scan.finished` entry records `listed` and `outside_window`. Given up: edits to posts older than the newest 50 are no longer seen, and a first scan stores only the newest 50. SNUH lists stop after 20 pages, so a board over about 200 posts still fails as incomplete | Fewer requests per day on large boards (대구가톨릭 공지: 50 opened instead of 121); the newest posts are the ones that change |
| File warnings and big files | **Decided 2026-11-10. Built and tested offline; migration `file_warnings_review` applied the same day.** **Big file:** an attachment over `MAX_FILE_BYTES` (20 MB) no longer fails its post: the post is kept with its text and other files, and the file is listed by name and the size the site shows, reason `too_large`, note "not downloaded: larger than 20 MB … open it on the hospital site", nothing stored; its stand-in hash comes from name + shown size + the site's own file id when it has one (R-BAY's download key), so a replaced file counts as a change even without a size; raising the limit later shows each formerly skipped file once as replaced (accepted). Only the file download itself may count as "too large": an oversized answer to R-BAY's file check fails the post as a site problem. **Admin "OK, reviewed":** only for FILE warnings (too large, unreadable, damaged, password-protected, broken zip): the server splits the reason and requires exactly one "<file>: <note>" per flagged file of the latest version, in order (notes never contain ";"; matched by file name, so reworded notes still count), so a post that failed to load (old state kept, fixed in code) cannot be cleared. The approval is stored in the **admin-only table `document_reviews`** (key = warning text + hashes of the flagged files, reason, who, when; migration `document_reviews_table` dropped the same-day columns on `documents`, which every reader could select); later scans with the same key keep the document `current`, other text or a replaced file flags it again. Order: conditional change first (refused if a scan changed the warning meanwhile, so nothing is logged for an OK that did not happen), then the audit entry (`document.review_acknowledged`); if the entry cannot be written the change is undone. After an OK the source's status follows (it used to stay red until the next scan): if its last scan was flagged only for posts needing review ("post <id>: …"), it shows the posts still left, or `ok` when none are; a whole-scan problem or a pause is never changed; guarded against a scan that ran meanwhile; a failure here never undoes the OK. Where: a button on the document page (admins) and an admin "Warnings" tab (`GET /admin/documents/reviews`, `POST /admin/documents/{id}/review-ok`) | A single big file used to drop the whole post, and on a first scan the post was never stored. Admins need to clear warnings they checked without them coming back every day |

| Scheduler | **Built 2026-11-06. Pause-column migration applied; one live `run_all` over sources 4, 5 and 6 succeeded (3 x ok in 193 s, no changes found, so the change-card path was not exercised).
