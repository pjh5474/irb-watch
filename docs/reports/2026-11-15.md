## 1. IRB calendar (CAL-1)

### Owner decisions (three question rounds)
- **Where sessions come from (CAL-O1):** manual entry plus AI proposals now. A platform admin starts "Find sessions" per hospital; the job writes proposals only.
- **Who enters them (CAL-O2):** platform admins enter and review; users who work on a project with that hospital propose.
- **Visibility:** everyone sees proposals, marked "not confirmed".
- **Reminders (CAL-O3):** reuse A2's days and recipients; proposals remind too, marked.
- **Scope:** sessions, tasks and the calendar in one build.
- **Step link:** the user picks; a hint is shown.
- **Kinds:** an admin list.
- **Views:** month, week and list.
- **Tasks:** simple fields; edit access changes them.

### Defaults I chose while building
- The AI's quote and its stored post are shown to platform admins only.
- A task whose assignee may no longer work on the project reminds the owner and PM instead.
- A passed cutoff is not repeated in the mail.
- The views are built by hand (no calendar library). Weeks start on Monday.

### What was built
- **Backend:** tables `session_kinds`, `irb_sessions`, `session_jobs`, `project_tasks` and column `pipeline_steps.target_session_id`, all server-only. Session service with the AI job (at most 15 posts, `store=False`, closing tags defused, every answer field checked again). Task service. `GET /calendar`. The step page's target meeting. Cutoff and task lines in the daily mail.
- **Frontend:** `/calendar` (month, week, list, filters, session panel, propose form), the step's "Target IRB meeting", the project's Tasks, the admin tab "IRB sessions".

### Code review: 10 findings fixed (owner's go)
- **Bugs:**
  - the AI search now reads public boards only, so dates from members-only boards never reach everyone as proposals (owner chose this);
  - a failed calendar reminder part writes a `mail.reminders_failed` audit entry instead of failing silently;
  - an empty post no longer stops the search (the reviewer's scenario could not happen, because the title is always there; the change is harmless).
- **Correctness:**
  - session searches run in their own 1-worker pool, so drafts are never blocked;
  - a task with `done: null` is refused;
  - an assignee id that is not a UUID gets a 422, not a 500.
- **Efficiency and cleanup:** the calendar reads access and pipelines once; the daily mail makes one access read per assignee; the services are built once per request; shared paging (`db/paging.py`) and time helpers.

## 3. Step page auto-save (decided, not built)
- **Owner:** the pipeline is "a work helper, not a data keeper". Waiting 1-2 s after an edit is very bad.
- **Decided:**
  - **scope:** all step fields, the step page first;
  - **saving:** a picked value saves at once, typed text about 1 s after typing stops; a status line shows saving, saved, or "not saved: reason · retry";
  - **two editors:** the later save wins, with a note to the other user;
  - **history:** one entry per save with the changed fields;
  - **no undo.**
- **When:** after the pipeline features. See decisions.md "Step page auto-save".

## 4. IRB pipeline phase C1: document lists and slots

### Owner decisions
- **Split:** C1 now (lists, slots, status, checklist, admin editor); C2 later ("use draft as final", copy a step to sibling sites).
- **Seed lists** for 초기심의 (12 documents, 5 required) and 변경심의 (7 documents, 3 required), confirmed by the owner.
- **Reference documents** (서류 바인더, 사전 검토, 참고자료) are slots users add; they never count.
- **Done rule:** "Mark final", as designed. A new upload sets the slot back to in progress.
- **Existing data:** open, not-yet-submitted steps get slots. The rest needs no care: the owner will reset the pipeline data, and only scanned board data stays.
- **After the review:**
  - **1a:** an empty hospital list is refused;
  - **2a:** a `listed` mark keeps copied slots locked;
  - **3a:** listed slots cannot be removed; the user marks them not needed.

### Defaults I chose
- Slots are made by the server when a step is made: the hospital's list for the type, else the global one.
- "Mark final" needs a file.
- Slots users add are not required.
- Only slots users add can be renamed or moved to another section.
- Reordering works inside a section.
- Lists stay server-wide (platform admin).

### What was built
- **Backend:**
  - table `step_type_documents` and functions `save_step_type_documents` and `reorder_step_documents`;
  - slot columns on `step_documents`;
  - lists (`services/pipeline_admin.py`): save whole, per hospital, back to global;
  - slots (`services/pipelines.py`): copied on new steps, upload into a slot, add, update and reorder, checklist = final or not needed;
  - admin routes `/admin/pipeline/step-types/{id}/documents...`, routes `document-slots`, a `PATCH` for documents and their order;
  - `step_types.required_documents` is no longer read or written.
- **Frontend:**
  - the step page groups slots into 신청서 및 통지서, 제출서류 and 참고자료;
  - each slot has its own upload, Mark final, Not needed, Reopen and move buttons, plus "Add a document";
  - changing a step to "submitted" with required documents not done asks first;
  - the admin "Documents" editor (`components/admin/document-lists.tsx`) has the global list and hospital lists.
